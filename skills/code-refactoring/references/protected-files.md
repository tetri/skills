# Protected Files

Categoria de arquivos que **não podem ser alterados/removidos** durante a refatoração sem justificativa explícita e aprovação do usuário. Muitas falhas documentadas de agentes vêm de mexer (ou deletar) exatamente nesses arquivos.

## O que é protegido

| Categoria | Exemplos | Por quê |
| --- | --- | --- |
| **Gerados por build/codegen** | output de build, clientes OpenAPI/GraphQL gerados, `*.pb.go`/`*.proto` gerados, migrations geradas, scaffold | Serão regenerados; mexer é inútil ou perigoso. Header "generated", `.gitattributes`, passo de geração no build = identificadores |
| **Infraestrutura como código** | Terraform, manifests Kubernetes, pipelines YAML/CI/CD, arquivos de deploy | Mudança sem intenção = impacto em produção; fonte da verdade do ambiente |
| **Schemas e contratos** | `.proto`, JSON Schema, contratos OpenAPI, migrations de DB | Alterar formato é mudança de comportamento de fronteira; exige expand-contract |
| **Wrappers load-bearing** | `withAuth()`, guards de permissão, validação de entrada, rate limiting, logging de auditoria | Remover como "limpeza" já causou lockout de produção; a presença é o comportamento |
| **Formatos serializados** | linhas de DB, arquivos de estado, payloads de API, caches | Representam contratos persistentes; o formato É a API |
| **Código de fronteira/entrypoint** | entrypoints públicos, hooks de framework, handlers de eventos | Qualquer mudança propaga para consumidores externos; requintam blast radius |

## Como detectar

1. Procure headers de arquivo: "generated", "DO NOT EDIT", "auto-generated", "code generated by".
2. Verifique `.gitattributes` (marcadores de linguagem/generado), `.editorconfig`, scripts de build que regeneram.
3. `git log --oneline -- <arquivo>`: arquivos que só mudam junto de geradores/versões são candidatos a gerados.
4. Confirme com o usuário quando houver dúvida — nunca adivinhe.

## Regras

- Arquivo protegido **nunca** entra no contrato de mudança sem aprovação explícita.
- Se a refatoração exigir tocar protegido: pare e **explique o motivo + plano de migração** (ex.: expand-contract para schema) antes de continuar.
- Wrappers load-bearing: para remover/mover, prove que NÃO é load-bearing (busca por usos, tests de integração, gate de segurança) — a justificativa "limpeza" é insuficiente.
- Arquivos gerados que ficam obsoletos após a mudança: não edite — **regere** (se possível) ou deixe para o pipeline.
- Dead-code em protegido: mesmo com busca limpa, não remova sem aprovação (falsa sensação de segurança — veja o protocolo de exclusão em equivalence-gates).

## Protocolo em caso de violação acidental

1. `git checkout -- <arquivo>` imediatamente (restaura do HEAD).
2. Revise o `git diff` para confirmar que nada protegido foi alterado.
3. Registre por que o arquivo é protegido na análise final (aprendizado).
